# Core integrity audit

Audit date: 2026-10-01. Scope: current `packages/core` source, its application/domain boundaries, provider composition, assistant grounding and CSV imports. The shared Graphify query returned other repositories and private evidence references, without PointUp source coverage; conclusions below come from live source and regression checks. No private evidence was used.

## Corrected behavior

- Provider composition defaults to configured real adapters. Unsupported integrations fail before writing a snapshot. Simulated balances require an explicit `allowSimulation: true` development/demo composition option; ordinary web/worker compositions do not enable it.
- Linking an account leaves expiry unknown unless explicitly supplied. Recording or syncing a balance preserves the existing expiry and account metadata, including when inserting historical observations. Merely observing a balance provides no evidence of qualifying provider activity.
- Transfer ranking no longer adds invented all-year demo bonuses. Bonus-window filtering accepts explicitly supplied windows, while default ranking has no live bonus feed.
- Assistant grounding includes actual observation dates, provenance and known expiry, distinguishes missing balances from zero, identifies totals as known points, and treats portfolio titles as quoted user data. The local expiration answer no longer recommends sync as a way to reset inactivity expiry.
- CSV parsing handles quoted newlines, escaped quotes, CRLF and a leading BOM, and rejects malformed records before writes. Import preflights membership identity across rows and existing accounts, preventing another membership's history from being merged into the user's existing provider link. Deleted memberships are skipped. Future observations are skipped rather than silently rewritten to the present.
- Balance creation and goal targets reject unsafe integers. New/updated goal associations reject deleted accounts in addition to enforcing ownership. Duplicate goal references are deduplicated and existing duplicate rows cannot inflate progress.
- 1Password Connect now receives the authenticated tenant ID and checks an exact server-supplied reference registry before fetching any secret. No registry means no access, including existing stored refs. Invalid path/control references are rejected; requests have bounded timeouts and reject redirects. Current host compositions supply no registry and therefore intentionally fail closed until a trusted provisioning path is added.

`packages/core/test/core-audit-regressions.test.ts` covers unconfigured/partially configured provider composition, expiry preservation for sync and backfills, unsafe balances, multiline/escaped CSV, malformed CSV, membership conflict preflight, future observation chronology, deleted account imports/goals and assistant grounding. Existing expiration/transfer tests were changed to assert the corrected behavior.

Commands ran from `packages/core`. The new vault suite contributes four tenant-authorization regressions. No real provider, Connect server or PostgreSQL was contacted for these tests.

## Remaining product gaps

- Transfer edges, provider valuation/expiry catalogs and curated deals are editorial, unverified static data. This audit did not establish current primary-source transfer eligibility, live ratios, offer windows or available awards. In particular, catalog inclusion is not evidence that a source currency transfers to that program. Before treating recommendations as actionable, validate supported transfer routes against current issuer/provider sources, retain source and checked-at metadata, and distinguish fixtures from verified offers.
- `allowSimulation` explicitly opts into a synthetic adapter, but the existing balance-source contract still only supports `sync` and `manual`. A future provenance migration should identify synthetic data separately throughout storage, UI, exports and model grounding.
- CSV imports remain append-only and do not deduplicate repeated exports. The web composition now supplies a portfolio unit of work: identity preflight and all import account, snapshot and activity writes are transactional, so persistence failures roll back the import. Hosts omitting the optional unit of work retain the earlier partial-write risk. Import also does not restore every exported account metadata field. A versioned import format, transactional writes and stable observation IDs would make recovery/re-import reliable.
- Linking and manual snapshot creation include their activity writes in the new web-composed portfolio transaction. Sync and other mutations still use separate repository operations. The opt-in portfolio PostgreSQL suite exercises the new transaction boundary; verification results are recorded in `database-verification.md`.
- Assistant context is built from separate account and goal reads, so concurrent writes can produce a mixed-time view. LLM output is not deterministically validated against the portfolio, and quoting user fields does not guarantee resistance to prompt injection. Add bounded history/context budgets and structured, validated recommendation output before relying on autonomous model actions.
- Existing goal progress can include retained historical balances after account unlink, because goal IDs are persisted separately from the account's active state. Decide whether goals should freeze, exclude or explicitly label those balances and apply the same behavior across all read surfaces.
- Null expiry currently combines unknown and non-expiring. The read model should represent those states explicitly so the UI and assistant can explain the difference.

## Database model and next migration proposal

Migration 0009 implements the normalized tenant-qualified goal relation, review-only quarantine of invalid legacy references, canonical tag arrays, staged snapshot/goal checks and scoped transactions for linking/manual balances/imports. See [portfolio-data-model.md](./portfolio-data-model.md) for the current model and compatibility details. The source observations and proposal below document the earlier audit state; activity references, validation of historic violations and other mutation boundaries remain open.

Source verification: `src/infrastructure/db/schema.ts`, initial migrations `0000` through `0007`, the Drizzle repository implementations, `domain/loyalty/trip-goal.ts` and `infrastructure/vault/one-password-connect-vault.ts`. These establish source-defined constraints; no live database schema/introspection or migration execution was performed in this audit.

Existing storage guarantees: `loyalty_account.id` is a primary key, `(user_id, provider_id)` is unique even for deleted accounts (`0001`), `balance_snapshot.loyalty_account_id` has an actual foreign key with hard-delete cascade (`0000`), and public share tokens are unique (`0004`). There is no local user table; Clerk identity strings are stored directly. Source-level TypeScript union annotations on status/source columns do not create database CHECK constraints.

Important gaps: `trip_goal.account_ids` is a comma-separated string, without account foreign keys or a same-owner constraint. Direct or mistaken repository writes can therefore link another tenant's account, and goal list/read paths load the referenced balances by ID without independently checking account ownership. Application create/update currently check ownership, but this is not a database guarantee. Duplicate account IDs also double-counted progress; this audit now deduplicates new/updated goal IDs and protects progress calculations for existing duplicate rows. `activity_event.account_id` has no foreign key and no tenant consistency constraint. Balance bigint values have no range check despite being deserialized as JavaScript numbers. Target-point/status/source/valuation invariants also lack database checks. `tags` permits up to 20 × 32 characters in the domain, but its comma-separated storage is only 512 characters. General repository update/delete predicates use an entity ID alone, relying on upstream ownership checks.

Proposed next migration (prepare and test before deployment):

1. Add unique `(id, user_id)` constraints to `loyalty_account` and `trip_goal`. Create `trip_goal_account(goal_id, user_id, loyalty_account_id)` with primary key `(goal_id, loyalty_account_id)`, foreign key `(goal_id, user_id)` to `trip_goal(id, user_id)` and foreign key `(loyalty_account_id, user_id)` to `loyalty_account(id, user_id)`. Composite references enforce same-tenant links. Hard-delete goal links should cascade; decide account unlink/hard-purge behavior explicitly, with soft deletion continuing to retain the parent account.
2. Before backfill, inspect existing ID strings, expand and deduplicate them, and separately report nonexistent and wrong-owner references. Preserve the original rows for operator review; never silently delete or reassign cross-owner records. Backfill only valid same-owner links, then switch reads/writes atomically to the normalized relation. Drop `account_ids` only after verification and a compatible deployment window.
3. Add database CHECK constraints for `0 <= balance_snapshot.points <= 9007199254740991`, `0 < trip_goal.target_points <= 9007199254740991`, permitted snapshot sources and goal statuses, and supported numeric valuation ranges. Stage constraints as `NOT VALID` where appropriate, inspect existing violations, then validate. Add a database-generated observation sequence or insertion timestamp to support consistent tie-breaking across latest/history/trend queries; random UUID lexical order does not encode insertion chronology.
4. Normalize tags to a relation/array or increase storage to the explicitly enforced serialized maximum. Prefer PostgreSQL `date` for valid goal dates. Preserve activity records on account purge; if adding tenant-qualified activity references, make only the account reference nullable on purge while retaining the activity owner, or model a separately immutable audit identifier.
5. Introduce transaction-scoped repository/unit-of-work support for imports and associated snapshot/activity writes. Test rollback and concurrent link/import conflicts against PostgreSQL, including wrong-owner direct inserts and hard-delete cascades. Consider row-level policies only with a tested per-request tenant context and separate deliberate worker access; merely adding RLS without connection-context handling would break shared pooled/worker operations.

Credential tenant boundary is separate from schema ownership: the original vault port resolved caller-supplied `op://vault/item` with a server-wide Connect token and no tenant authorization. This audit fixes that access path with a tenant-qualified trusted reference registry; unconfigured compositions deny all references. The next provisioning step must register approved references from trusted server-side ownership evidence, never request input or existing unverified rows. Regression tests prove unauthorized/default-denied requests never call Connect or the provider gateway. This finding is conditional on enabling the former shared vault adapter, not proof of historical secret exposure.
