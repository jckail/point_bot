# Production rollout: migrate before activating new hosts

Status: implementation plan, not a deployment result. Source reviewed in the integration worktree after `d9ffc38` on 2026-10-02. No AWS calls, application edits, installs, builds or database checks were performed for this audit. Graphify was queried first; it returned unrelated corpus/investigation paths rather than this repository's deployment source, so findings use live files below.

The release must change the present order from **verify → full stack deploy → migrations** to **verify → publish immutable images → migrations → activate candidate application/worker hosts**. A failed migration must prevent every candidate web, bot, MCP and scheduled worker activation. Merely placing the migration task construct earlier in CDK does not create a migration-completion dependency.

The previously reported expired AWS session, zero repository secrets and nginx response from the public site are external gates, not proof of stack ownership or successful deployment. An authorized operator must establish AWS account/region, active `TemplateApp` ownership (or confirmed absence), DNS/ALB/certificate ownership, valid OIDC deployment access, approved production environment, real Clerk keys and backup/restore access. Do not invent role ARNs, populate generated placeholders with fake provider keys, or assume the observed public host is this stack. Record verification timestamps; CI success alone establishes none of these external facts.

## Preserve resource identities

Keep stack name `TemplateApp` and current construct paths, particularly `Vpc`, `Database`, `Cluster`, `Service`, `AppImage`, `WorkerImage`, `MigrationTaskDef`, `MigrationSecurityGroup`, secrets and optional service/schedule paths. Do not extract existing resources into a new stack or conditionally remove workload constructs as a first implementation: that can propose deletion/replacement. Review the actual deployed template and CloudFormation change set before applying changes; reject database/network replacement and unexpected removals. CloudFormation change sets expose replacement scope but do not prove a migration or rollout will succeed ([AWS guidance](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html)).

Add an explicit **first-create inactive** configuration in `AppStack`: create the same workload constructs with web/bot/MCP desired count 0, autoscaling minimum **and maximum** 0 (or suspended policies plus bounded zero target), and all four EventBridge schedules disabled. A workload property override must not suppress its construct or recreate it under another parent. Verify no event target or scaling rule can start a host. Keep the inactive mode unavailable to the upgrade path: silently setting a live production service to zero is not an upgrade strategy. The workflow must check stack absence before an inactive creation and stop on ambiguous/failed lookups.

Give `Migrate` only the DB secret fields and required nonsecret migration settings. It needs no Clerk/provider/aggregator credentials. Preserve its role/log/SG construct identities; do not grant public ingress. Optional feature secret creation belongs before feature activation, with real values verified through metadata/config checks rather than printing secret contents.

## Existing-stack upgrade path

Implement a bounded helper, for example `infra/scripts/prepare-migration-task.mjs`, and workflow tests before enabling deployment:

1. Verify the exact commit through reusable CI. Synthesize one candidate cloud assembly using the reviewed production context and Clerk publishable build key. Record commit, asset hashes/image digests, region/account, expected journal tail and assembly hash as a nonsecret release manifest. Use the **same assembly** for image publication and later CDK deployment; do not resynthesize with different context after migrating.
2. Publish candidate Docker assets without executing a CloudFormation update. Use a pinned CDK asset publisher and the assembly's asset manifest, with account/region and destination validation; add the explicit publisher dependency/version when implementing. CDK's asset assembly describes image publication separately from stack resources ([asset documentation](https://docs.aws.amazon.com/cdk/v2/guide/assets.html)). Check ECR digests before running a migration; never derive image locations from untrusted branch strings or use mutable `latest`.
3. Read the current stack outputs `ClusterArn`, `MigrationTaskDefinitionArn`, `MigrationSubnetIds`, `MigrationSecurityGroupId`. Validate account/region, nonempty IDs and existing roles before mutation. Describe the current migration task definition. Build a registration payload from an allowlist of its supported ECS input fields, retaining its real execution/task roles, log configuration, Fargate/architecture/CPU/memory/network settings and DB secret references. Replace only the `Migrate` image with the published candidate worker URI/digest, command with `["migrate"]`, and remove unrelated secrets from that container. Reject sidecars, extra containers, overrides or role changes until explicitly supported and tested.
4. Register a fresh revision of the existing migration task family and run **that exact ARN**. Registration is an out-of-band one-off artifact; it does not update the CDK-owned task definition resource or any running service/schedule. Record its ARN/digest in the manifest and clean up only the registered revision after completion when safe. Never run an old task-definition output expecting it to contain candidate SQL. No guessed IAM role or secret ARN is acceptable.
5. Run in the existing private subnets with the migration SG and `assignPublicIp=DISABLED`. Capture full structured RunTask output, fail on any `failures` or absent task ARN, then await termination with a bounded workflow timeout. Describe the exact task and require `Migrate.exitCode === 0`; missing container/exit code, startup failure, timeout, stopped task or nonzero exit blocks release. Retain task ID, stop reason and private log reference for diagnosis, without echoing secret-bearing request payloads. AWS explicitly returns launch failures separately from tasks ([RunTask API](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_RunTask.html)).
6. Inspect the managed journal through the operator-approved private database path, compare the release manifest's expected migrations/hashes with applied entries, and perform bounded schema checks for the new tables/constraints. Migration exit zero plus an inspected journal are the promotion gate. Migration-lock timeout blocks release; do not bypass the lock or stamp journal rows to force progress.
7. Only now execute the reviewed full-stack CDK change set from that assembly. This updates web/bot/MCP and all schedule images. Wait for CloudFormation/ECS stability and health, inspect authenticated read-only smoke results and bounded failure metrics, and record the deployed digests. Feature/provider/live evaluation smoke remains explicit opt-in; no paid calls are required to publish a release.

This path requires narrow IAM additions: current stack/template/output inspection, `ecs:DescribeTaskDefinition`, bounded `ecs:RegisterTaskDefinition`/cleanup, ECR asset publication via the real bootstrap publishing role, and RunTask/DescribeTasks. Scope RunTask to the migration family and cluster, PassRole to the actual migration roles with ECS condition, and use conditions/tags where registration cannot be resource-scoped. Test the policy; do not retain today's broad `iam:PassRole role/*` as an assumed least-privilege result. Changing IAM/OIDC bootstrap remains operator-authorized infrastructure work separate from this document.

## First deployment path

First creation cannot run ECS migrations before the VPC/database/cluster/roles exist. It may create infrastructure **with all hosts inactive**, not deploy an ordinary full stack and hope migrations finish first.

1. Confirm stack absence, synthesize the inactive-first-create assembly, inspect its template/change set, publish its assets and create the same `TemplateApp` resource identities with zero hosts/disabled schedules.
2. Verify RDS/network/real migration execution role availability. Populate legitimate application secrets through the authorized Secrets Manager path; generated placeholders are not valid credentials. Keep public traffic/DNS gated.
3. Run the created candidate `MigrationTaskDefinitionArn` (`Migrate` DB-only) and require the same task/journal/schema gates as upgrades. Empty databases use managed SQL from the beginning. Existing unmanaged databases require the separate adoption process below.
4. Promote by synthesizing the active configuration from the same commit, feature context and immutable images. Check that the template diff changes only reviewed activation/scaling/schedule and related configuration properties, preserving resource IDs. Activate services/schedules after successful migration, wait for health, then direct verified TLS DNS traffic. Failure before promotion leaves inactive resources for diagnosis; it does not justify destroying the database.

## Schema adoption, availability and rollback

Before migrating an existing database, inspect the actual managed journal and physical schema. Distinguish clean managed history, empty database and legacy unjournaled schema. Compare migration files/hashes and expected columns/constraints; unexplained drift or historical owner/provider mismatches need an operator decision. Do not rerun old create-table SQL over a populated legacy schema, silently assign current history, delete mismatched rows, or manufacture provenance. Migration 0019 retains v0 rows and installs its owned-account FK `NOT VALID`; inspect the retained mismatches and constraint validation state without claiming every historical row has new provenance.

Take a named pre-release RDS snapshot, confirm completion and retain its ID/time, applied journal, old service task revisions/image digests and infrastructure template. Existing RDS settings are seven-day backups, deletion protection and snapshot removal policy; these do not substitute for a verified restore procedure. Test restoration into a separate instance and verify ownership/access before any production release that depends on recovery.

Classify pending SQL for compatibility with the **currently running** release. Additive schema still includes indexes/constraints and migration 0018's archival exclusive-lock behavior; inspect lock duration/table size and set an operator-approved maintenance window when live writes must pause. Disable schedules and explicitly drain/restrict affected writes before incompatible migrations, with a recovery plan for existing hosts. Do not assume the session migration advisory lock stops those writes. Gate unbounded locks/large scans with staging evidence and an explicit operational timeout rather than silently failing open.

Migration failure: keep old hosts/images and blocked promotion, inspect rollback/journal/task logs and actual table state. Never repeatedly rerun an unchanged failure or auto-run a down migration. App rollout failure after successful additive migration: restore the previous application assembly/images **only after confirming old-code compatibility with the new schema**, leave additive schema in place, and inspect ECS circuit-breaker recovery. Destructive/incompatible changes require a forward fix or approved database restore; restoring a pre-release snapshot loses later writes and therefore requires an explicit recovery decision. CloudFormation/ECS rollback does not roll back database state.

## TLS and feature activation gates

Current web `Service` provisions default public HTTP and outputs an HTTP `LoadBalancerUrl`. Implement explicit approved web certificate/domain/origin configuration with HTTPS listener + HTTP redirect and stable construct identity before public Clerk/cookie/PAT/SIWC traffic. Validate the deployed change set, ACM account/region/domain and DNS ownership. Registered SIWC HTTPS callback is not evidence that the web ALB has TLS; SIWC remains disabled without the approved client, genuine secret where applicable, and exact registered callback.

MCP currently requires its own certificate/domain and redirects HTTP, but `POINTUP_URL` defaults to the **HTTP web ALB** if `mcpPointupUrl` is omitted. Require a verified HTTPS upstream for public deployment and configure the actual canonical web origin; otherwise MCP forwards bearer credentials across an unencrypted upstream hop despite its own TLS listener. Preserve host/origin restrictions and never put a fixed PAT into ECS environment/CDK outputs. Optional bot follows its independently reviewed certificate/auth policy.

## Implementation acceptance tests

- CDK snapshots/assertions: stable logical IDs between active/inactive modes; first-create service counts 0, zero scaling capacity, all four rules disabled; unchanged VPC/database/log/role paths; DB-only migration secrets; web TLS redirect and MCP HTTPS upstream enforcement. Assert upgrades cannot accidentally select inactive mode.
- Offline workflow/helper fixtures: verification-only/unconfigured paths make zero AWS calls; failed verify/publish/migration cannot call CDK deploy or update services; existing-stack upgrades never deploy before successful candidate migration; first-create is accepted only on confirmed absence; outputs/roles/regions/digests are validated; registration keeps roles/DB secrets and uses candidate image; malformed RunTask/`failures`/missing exit/nonzero/timeout block promotion.
- Release-manifest tests: same assembly/assets across migrate/deploy; task uses expected SQL/journal revision; journal mismatch blocks activation; candidate schedule images cannot execute before gate; production context cannot enable dev auth/bootstrap/dev token.
- Root-owned staging/PG verification: managed migration/adoption fixtures, SQL rollback/lock behavior, old/new code compatibility, inactive creation/promotion and ECS failure recovery. Real AWS smoke and restore rehearsal remain external operator gates. Unit/synth fixtures do not establish public production readiness.

Proposed implementation owners: deployment helper/workflow and IAM tests; bounded CDK inactive/TLS/upstream configuration; operator journal/adoption/backup review; root verification/release. This document changes no deployment behavior. The current workflow must remain an identified release blocker until the migrate-before-activation implementation and its gates are reviewed.
