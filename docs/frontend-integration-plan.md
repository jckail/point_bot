# Frontend overhaul integration plan

Read-only audit, 2026-10-02. Compared current live `point_bot-integration` source (root identifies release candidate `d9ffc38`, following `eaa2bea`) against preserved native `point_bot-release` source (`4303c05`). This is a port plan, not a claim of browser verification or a runtime change. Graphify was queried first; it returned unrelated portfolio/encore/blackbox paths rather than PointUp frontend coverage. All findings below were checked against live files. No browser tabs, application servers, dependency installs, builds, tests, Git commands or provider sessions were opened/run for this audit.

## What still needs the frontend overhaul

The integration has acquired the assistant/review surfaces and backend protections, but the main visual and portfolio-navigation overhaul remains substantially unported. Its landing page still uses the earlier dark centered gradient hero; the dashboard still presents a long series of sections without native section navigation; account filtering remains tags-only. The native reference has a light travel-oriented landing layout, ticket illustration, clearer portfolio hierarchy, search/type filtering, and several accessibility and truthful-copy improvements. Backend work alone does not deliver that product experience.

Static accessibility evidence: existing `ink-faint` (`#5f6a8f`) computes to approximately **3.24:1** on `surface` (`#121a30`) and **3.56:1** on `midnight` (`#0b1020`), yet appears in small captions, tags, navigation and plan caveats. Native faint text (`#596d82`) on white computes to **5.34:1**, and white on native primary blue (`#215bcc`) to **6.12:1**. These are calculations from source tokens using sRGB relative luminance, not measured rendered contrast; opacity, overlays, charts and hover/focus variants still require browser inspection. The port should audit actual text/background combinations rather than assuming all light-token substitutions pass.

## Already integrated or worth preserving

- The assistant panel has keyboard Escape/return focus, expanded/control attributes, a labeled message input, live conversation log, deadlines, support references, retry state and review navigation. Integration additionally bounds outgoing history to 32 KiB and accepts the existing `x-request-id` header. Native wholesale replacement would lose these newer protections.
- `reviewed-assistant-actions.tsx` already has request serialization, stale/expired guards, status/alert announcements and focus return. Keep these while restyling. Browser approval and immutable proposals remain the existing flow.
- `form-feedback.tsx` is identical between trees: alert/status feedback and pending-aware submit helper are already available. The gap is sync/review form adoption, not a missing helper requiring duplicate implementation.
- Manual balance, membership-number, notes, import, and recently-unlinked components matched the inspected native versions. Preserve their functional code and apply layout/tokens in place.
- `BestRedemptionsSection` is PR14-only in this comparison; it renders ranked optimizer plans, active bonuses, expiry holdings, ordered transfer steps, shortfall/fundability, confidence and honesty caveats. Keep the server query, DTO conversion, component and its place under opportunities. Native dashboard lacks it entirely.
- PR14 dashboard recognizes additional kinds including car rental, cruise, rideshare and dining. Preserve complete catalog coverage, kind badges/group labels, branded IDs, current value math, custom valuations/settings, pinning, tags, demo, history, export/import, shares, soft unlink/restore and public share view.
- Integration's local Sora/Inter font files and `next/font/local`, `force-dynamic` root, `isDevAuth` conditional Clerk loading, session helpers, server action signatures and ownership checks are deliberate compatibility points. Native unconditional Clerk imports/system fonts are not a safe wholesale replacement.

## Assets and brand consistency

Both trees contain the same three public asset names: `brand/logomark.svg`, `brand/logo-horizontal.svg`, and `brand/logomark-mono.svg`. There are no native photography/raster hero assets missing from integration: the ticket/route map and feature icons are inline SVG/markup in native `app/page.tsx`. The mono asset matches; color mark and horizontal lockup differ in palette and font references. The ascent geometry/PointUp wordmark are shared.

A complete visual port must update `styles/globals.css`, `components/logo.tsx`, `app/icon.svg`, `app/opengraph-image.tsx`, both color SVG assets, `components/clerk-provider.tsx`, and `docs/brand.md` consistently. Keep mono geometry and accessible asset labels. The native horizontal asset assumes Avenir Next is installed; retain the bundled Sora-based wordmark or use an explicitly reviewed outlined asset so Linux/browser rendering does not depend on an unavailable proprietary font. Do not mix a blue/light app with violet/dark favicon/social/auth cards unintentionally. Retain local font loading and avoid new third-party image/font calls.

Native has a skip link to a wrapper div but no explicit programmatic-focus treatment. Port a working skip link to the existing main-content wrapper with a suitable focus target (`tabIndex=-1` where needed); do not create nested `<main>` landmarks. Preserve route `<main>` elements. Add a visible global focus rule that survives existing `outline-none` utility usage, verify native scroll-margin behavior against sticky header, and test reduced motion rather than only copying CSS.

## Browser and functional release gates

Static source review is insufficient to claim responsive layout, keyboard access, real focus or auth-modal appearance. Root should reuse one owned development server/worktree and one owned browser tab for the following sequential checks; do not inspect, navigate, close or reuse unrelated user tabs. Reuse that same tab across routes/viewports. Record its owner/tab ID plus server PID, port and log; close only temporary resources owned for this verification. Expensive checks stay behind `agent-heavy-check`; root coordinates the single verification owner and other agents consume its result.

1. Landing at narrow/mobile and desktop widths: hero/ticket/feature/program strip flow, no page-level horizontal overflow, illustrative labels, CTA and how-it-works anchor, footer/brand consistency. Check header when signed out and signed in; preserve dev mode without Clerk keys. Verify focus-visible/skip link and reduced-motion behavior.
2. Empty/demo/populated dashboard: discover link/demo/manual update, all section anchors land visibly below sticky header, stat typography/counts, 1/2/3-column cards, search/type/tag combinations and clear reset, no hidden optimizer/deals/expiry/goals/activity/share/restore/manage features. Use local fixtures; no live provider account required.
3. Keyboard-only forms: link/manual/import/notes/membership/goals; pending sync/card action prevents duplicate submission and status/error is readable. Check long program/membership/tag/share URL values, error copy, progressbar announcement and tab order at zoom. Validate source-owned current flows rather than changing API semantics to fit native JSX.
4. Assistant and Agents: open/close/Escape/focus return; failed chat retains conversation/support reference; proposal links arrive at `#review-actions`; human approval/rejection stays browser-only. Observation held/rejected/expired/current review display and token one-time/revoke/provider-consent flow remain intact. Restyling must not hide review controls or expose private provenance.
5. Account detail/public share/settings: owner/not-found behavior, history/manual update/unlink/restore, connected-identity statuses, no overflowing charts/table/text, correct route links. Check a representative optimizer plan with caveats and a no-plan state.
6. Auth-mode source/route gate and production rendering: keep conditional auth loading and local font assets; verify Clerk appearance only with root-approved auth fixture. Inspect generated favicon/social image after the cohesive asset update. Run final required project checks once after changes settle.

The repository's existing `e2e/playwright.config.ts` explicitly tests MCP through HTTP `APIRequestContext` with **no browser**. Those passing tests do not establish the frontend browser gates above. Add only bounded functional/browser checks needed for changed behavior; do not label backend/API CI as visual acceptance. Missing browser evidence should be reported precisely as unverified rendering/interaction, without inventing screenshots or claiming no regressions.
