# Loyalty provider integration capabilities

Evidence checked **October 1, 2026**, against the 13 IDs in `packages/core/src/domain/loyalty/provider.ts`. This audit uses official program, help, developer and vendor engineering pages. No provider registration, partnership application, authenticated account access or live balance API call was performed.

**No public, self-service API contract for reading arbitrary users' personal loyalty balances was verified for the catalog.** This is a research result, not proof that private APIs do not exist. Documented partner APIs and consumer websites are distinct capabilities. A banking account balance API does not establish rewards-point access. A points redemption API does not establish permission to aggregate balances.

## Catalog and usable starting points

These are official entry pages for a person to open and sign in themselves. They are not OAuth authorization endpoints or guarantees of automated extraction permission. User login, MFA, passkey and consent remain on the provider's site. Some links lead to a program/help page with its own sign-in action rather than a stable deep account URL. A successful public-page fetch does not validate an authenticated balance selector.

## Verified developer/partner paths

- **Chase:** [J.P. Morgan's official registration page](https://developer.jpmorgan.com/register/) says Chase Developer access is by invitation and limited to developers/businesses with a Chase relationship. It requests company, use case and representative details. This establishes an access gate, not a rewards endpoint. Obtain written product eligibility, scopes and data contract before writing a native Ultimate Rewards adapter.
- **Amex:** [Open Banking](https://developer.americanexpress.com/open-banking) describes customer-authorized Account Financials and Account and Transaction products and an invite request. [Integration process](https://developer.americanexpress.com/documentation/how-it-works) describes product access, possible contracts, sandbox and production approval. Those pages were publicly indexed, but direct retrieval returned an application shell/error in this audit; the locked specifications were not inspected. Membership Rewards fields and US eligibility remain unresolved. General OAuth documentation is not evidence of rewards scope.
- **Hilton:** [official API catalog](https://developer.hilton.io/api-catalog/hospitality-partner/) explicitly requires an agreement and grants access per endpoint. Public sections cover distribution, internal diagnostics and security. Request access for the specific intended loyalty-read use case; do not treat reservation/realm endpoints as an Honors balance API.
- **Capital One:** [official engineering article](https://www.capitalone.com/tech/software-engineering/inside-shop-with-rewards/) describes Shop with Rewards as available to approved card partners, including balance/redemption/refund at POS. It describes a dollar-denominated rewards response. A relevant partnership, approved product contract and supported miles field would be needed for a native catalog adapter. Existing partner access has not been obtained.
- **Citi:** [official developer portal](https://developer.citi.com/) publicly advertises consumer account dashboards and Pay/Shop with Points. Its publicly retrievable content was incomplete during this audit; country/product eligibility and current rewards specifications are unverified. [Account Reporting Balances](https://developer.citi.com/apidocs/account-reporting/balances/balances-overview/) describes bank balances in local currency, not ThankYou points. Obtain the actual rewards product specification and access approval first.
- **United:** [official NDC agency guide](https://united.business/NDC-travel-agencies) describes agency/technology-partner distribution connections. This is evidence of a distribution integration route, not permission to read arbitrary personal MileagePlus balances.

For Amtrak, Bilt, Delta, American, Marriott, Hyatt and Rakuten, the reviewed primary sources establish consumer account/program paths; they do not establish a public self-service balance API. Private partnerships may exist. No production adapter should invent endpoints, scopes or access rights from website network calls.

## Next implementable adapters and acceptance checks

Start with **Amtrak and Bilt guided imports**, then the existing airline/hotel reader: open the verified official page, let the member complete sign-in/MFA, inspect only visible account balance text on an allowed HTTPS host, present the provider/currency/account/amount for confirmation, and save only that confirmed observation. Never submit login forms, extract cookies, automate captcha/MFA, or replay private website APIs. User consent does not independently establish vendor authorization; confirm the provider terms/applicable integration permission before distributing provider-specific capture. If the page cannot identify one unambiguous redeemable balance, offer manual entry.

Add sanitized, consented fixtures for each authenticated page variant before declaring it supported. Required cases include signed-out templates, pending vs available amounts, status vs redeemable units, multiple cards/accounts, zero balance, advertisements, locale separators and unexpected redirects. Request exact host permissions only for a user-chosen provider; do not grant broad third-party iframe or payment-host access. Source URL alone is insufficient proof of account ownership.

Keep optional vendor API adapters disabled until the approved contract supplies the authentication method, consent scopes, exact endpoint, unit/account semantics, rate limits and revocation behavior. Existing generic aggregator configuration is not proof of access to these vendors. No vendor credentials, enrollments or external messages were created here.

## Catalog issues observed during this audit

These discrepancies were observed in the catalog at the start of this audit. This document does not modify the catalog; check the current source for subsequent corrections:

- Amtrak's [current FAQ](https://www.amtrak.com/guestrewards/amtrak-guest-rewards-faqs) says points expire after **24 months** of inactivity, with a credit-card-holder exception; the catalog at audit start recorded 36 months.
- United's [official 2026 MileagePlus page](https://japan.united.com/mpjapan) says miles do not expire; the catalog at audit start recorded 18 months.
- Hilton [official terms](https://www.hilton.com/en/hilton-honors/terms/) require eligible activity within **24 consecutive months** to avoid forfeiture; the catalog at audit start used null. Account-specific guarantees/exceptions require additional modeling.
- Bilt [official Bilt Cash guidance](https://support.biltrewards.com/hc/en-us/articles/40132420650509-Bilt-Cash) explicitly separates Bilt Cash from Bilt Points. Rakuten [official account guidance](https://www.rakuten.com/help/category/account-questions-26578301675411) separates pending/confirmed earnings and payout modes. Their monetary balances require currency-aware modeling rather than an integer points conversion.

This audit verifies source-qualified entry paths and access constraints. It does not certify current DOM selectors, vendor terms compliance, installed browser permissions, production API admission, or live synchronization.


## Public catalog and linking guidance

The public provider catalog now includes optional `capabilities` metadata: an official account/program entry URL, collection methods, reviewed page-capture readiness, balance-unit guidance, native API access readiness and `automaticSync: requires_verified_adapter`. The deployment-neutral sync value means the catalog does not infer working program access from generic aggregator configuration. Existing clients can continue reading older provider DTOs without this field. The public providers endpoint constructs the pure `ListProviders` use case and requires no database connection, server container or secret configuration.

The link form shows the selected program's balance unit and official entry link before linking. The six existing airline/hotel page readers support user-reviewed capture; their public links do not certify current authenticated DOM selectors. Cards, Bilt and Amtrak offer manual entry. Bilt guidance keeps Bilt Cash separate from Bilt Points, and Amtrak guidance separates Available Points from Tier Qualifying Points. Rakuten's catalog record remains for compatibility, but its ambiguous cash/points payouts offer no numeric collection method; the link form directs members to their actual Amex/Bilt points payout program and does not offer a Rakuten link submission. No USD amount is converted into points.

Primary sources were checked again during implementation on October 1, 2026. [Amtrak's FAQ](https://www.amtrak.com/guestrewards/amtrak-guest-rewards-faqs) still directs members to Account Overview for points; [Rakuten account guidance](https://www.rakuten.com/help/category/account-questions-26578301675411) distinguishes Cash Back Activity from Points Activity; [Bilt's cash guidance](https://support.biltrewards.com/hc/en-us/articles/40132420650509-Bilt-Cash) treats Bilt Cash separately from points. API-readiness `partnership_required` records a documented gate, rather than a verified personal-balance endpoint: [Chase invitation-only developer access](https://developer.jpmorgan.com/register/), [Hilton endpoint-specific agreements](https://developer.hilton.io/api-catalog/hospitality-partner/), and [Capital One approved-partner Shop with Rewards](https://www.capitalone.com/tech/software-engineering/inside-shop-with-rewards/). Other entries remain `not_verified`.

The official entry URLs in the table above were revisited. United returned its JavaScript shell, American returned limited support-page content, ThankYou returned a redirect page, Hyatt's official sign-in redirected to its current official account host but could not be fetched by the research tool, Bilt's root page did not yield readable content, and Chase's older gift-card guide timed out. These are public-fetch limitations, not evidence that account login or capture works. [Chase's current official rewards-details page](https://www.chase.com/personal/credit-cards/rewards-details) independently documents account rewards access. No authenticated provider page, live balance API, registration or vendor credentials were used.

Focused verification passed in the Linux validation mirror: **9 core capability/DTO/OpenAPI tests** and **1 public-provider-route test**. The latter loads the real route while a private-container import is configured to fail, establishing that catalog responses do not construct server services. No full suite, production build, provider-session browser flow or live vendor balance request was run for this bounded change.
