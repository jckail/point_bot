# Synthetic assistant evaluations

The evaluation dataset lives in `apps/web/src/server/assistant-agent/evaluation/cases.ts`. Ten invented cases cover numerical grounding, old observations, uncertain award availability, provider prompt injection, exact reviewed balance/goal proposals, read-only authority, credential refusal, account ownership, and missing data. Fixtures have synthetic membership/notes/credential canaries and in-memory services; they never connect to a database, provider account, browser, or production portfolio. Foreign accounts fail fixture ownership checks. Production repository ownership is independently tested by the core action suite.

The regular web test suite adds eleven tests that run the real Agents SDK with an injected protocol model or check the evaluator. They verify actual tool results, owner scoping, instruction delivery, private field projection, immutable pending proposal values, rejected foreign/extra owner fields, five-proposal limits, sanitized usage and failure summaries, case selection before inference, and bounded trace teardown. A scripted model does **not** demonstrate that a live model obeys policy or resists injection. The opt-in live test is skipped during ordinary tests.

Use the runner from the repository root after installing existing dependencies:

```sh
node scripts/evaluate-assistant.mjs --help
node scripts/evaluate-assistant.mjs --live --model YOUR_EXPLICIT_MODEL --output /tmp/pointup-eval-new.json
node scripts/evaluate-assistant.mjs --live --model YOUR_EXPLICIT_MODEL --case provider-injection --output /tmp/pointup-injection-new.json
```

Supply `OPENAI_API_KEY` through your existing secure environment. The runner never loads `.env` files, chooses a model, reads stored credentials, or starts inference without `--live`, an explicit model, and a key. No live evaluation was run during implementation. A full run has ten sequential cases, at most five model turns per case, a 30-second per-case deadline and 1,200 output tokens per model request. It can incur inference charges; these limits are not a monetary budget. Provider retries and requests already in flight may outlive cancellation. `--case` can repeat to select a bounded subset. Unknown cases fail before inference.

The output is created exclusively: an existing file is never overwritten. Schema version 1 includes dataset version, model, injected/live mode, case IDs, pass/fail/unavailable status, named boolean checks, latency, measured token usage and model requests. `usageAvailable` distinguishes absent usage from observed zero; partial usage may be available on failure. It excludes prompts, replies, payloads, account identifiers, provider errors, API keys and private fixture fields. `passed` means all automated smoke checks passed; `semanticReviewRequired` remains true. Keyword checks can miss unsafe paraphrases or flag good alternatives. They are diagnostic checks, not release approval or a calibrated judge.

For each dataset case, apply its `rubric` to the model's behavior in a controlled synthetic run: verify numbers and dates, explain uncertainty, reject provider text as authority, refuse secrets, preserve ownership, and distinguish a pending proposal from approval or execution. The checked-in runner intentionally does not persist the reply; qualitative review needs a separate explicitly controlled synthetic inspection. Never replace fixtures with real user conversations or portfolios. Run candidate and baseline models against the same dataset/version, compare case checks, usage and latency, and manually inspect any differences before accepting a change.

Tracing is disabled by default. `--trace` requests SDK export with the runtime's `traceIncludeSensitiveData: false`; `OPENAI_AGENTS_DISABLE_TRACING=1` still disables export globally. The runner flushes only once during CLI teardown with a three-second wait. `tracingRequested`, `tracingEffective`, and `traceFlush` distinguish intent, the global disable gate, and flush completion/timeout/failure. Completion does not prove remote delivery; `traceDeliveryVerified` is always false. Chat requests do not force a synchronous flush. For persistent ECS servers, normal SDK batching remains asynchronous.

Official references: [SDK integrations and observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability) and [repeatable agent evaluation workflows](https://developers.openai.com/api/docs/guides/agent-evals). The installed SDK types are the authority for the current TypeScript `Model`, `Usage`, runner events and trace-provider flush APIs.
